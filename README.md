# PDF_Analyzer

Tooling to extract structured product information and image references from catalog PDFs.

## Project structure

Expected layout in the project root:

- `Extract.py`
- `input_pdfs/`
  - All input catalog PDFs you want to analyze.
- `output/`
  - Generated JSON files (created automatically).
- (Optional) other helper scripts, config files, etc.

## Dependencies

- Python 3.10+ recommended
- `pdfplumber`, `PyPDF2` for PDF/text handling
- `opencv-python`, `numpy`, `Pillow` for image processing
- `openai` for GPT-based image filtering and classification

Make sure you install the required packages (example using the Python launcher on Windows):

```powershell
py -m pip install pdfplumber PyPDF2 opencv-python numpy Pillow openai
```

## What Extract.py does

`Extract.py` processes all PDFs in `input_pdfs` and writes a combined JSON file into `output`.

Per SKU it tries to extract:

- **Identifiers**
  - `sku`
  - `pdf_source` (PDF filename)
  - `merged_pdf_page` (list of internal page numbers where the SKU appears)
  - `source_pages` (printed page numbers, when detectable)

- **Technical attributes** (when present in tables or text)
  - Pressure (`pressure_min_bar`, `pressure_max_bar`, `pressure_bar_list`)
  - Flow/capacity (`flow_l_min`, `flow_l_min_list`, `flow_m3_hour`)
  - Power (`power_hp`, `power_kw`, plus some `*_raw` fields)
  - Dimensions (mm and inch, single values or lists)
  - Voltage, frequency, RPM
  - Volume, weight, noise level
  - Temperature / dew point
  - Materials, connection types, features
  - Extra items such as pistons/cylinders amount, connection size in inch

- **Descriptions / product grouping**
  - `description`, `description_raw`
  - `product_type`, `product_category` (derived from surrounding titles / headings)

- **Images per SKU**
  - For each page where a SKU appears, candidate product images on that page are linked to the SKU.
  - Images are stored as a list under the `images` key, each entry like:

    ```json
    {
      "pdf_source": "catalog.pdf",
      "page": 12,
      "index_on_page": 0,
      "bbox": { "x0": 123.4, "y0": 456.7, "x1": 300.1, "y1": 700.2 },
      "image_path": "images/12345_catalog_p012_img000.webp"
    }
    ```

  - The `image_path` field (when present) points into the project-level `images/` folder, where cropped WEBP files are written with names like:

    ```text
    <safe_sku>_<safe_pdf_name>_p<page>_img<index>.webp
    ```

  - `Extract.py` uses several heuristics and a GPT-based filter to skip layout/placeholder images and keep likely **product** images that are closest to the relevant tables.
  - This gives you SKU-level image references that can be consumed directly in a webshop feed.
  - `PyPDF2` (for some earlier experiments; main script uses `pdfplumber`)


### OpenAI / GPT configuration

Some of the image filtering and matching logic in `Extract.py` and the post-processing script `classify_images_with_gpt.py` use GPT-4o via the official `openai` Python client.

Set your API key as an environment variable before running these scripts:

```powershell
$env:OPENAI_API_KEY = "sk-...your-key-here..."
```

On other platforms, export the same variable in the appropriate shell.

## pdf24-style image export helper

In addition to the images generated by `Extract.py`, there is a standalone helper script that behaves like a pdf24-style bulk image extractor, but with **SKU-aware naming**:

- **Script**: `local_extract_images.py`
- **Input**: all PDFs in `input_pdfs/`
- **Output root**: `airpress-style-images/`

Behavior:

- **Per-PDF output folders**
  - For each input PDF, images are written under:

    ```text
    airpress-style-images/<pdf-file-name>/
    ```

- **Category + SKU-based filenames**
  - Uses PyMuPDF to iterate embedded images on each page.
  - Uses `pdfplumber` to read the same page and:
    - Derive a **category name** from the top header strip.
    - Aggregate SKUs from all tables on that page into a compact **SKU tag**.
  - Each kept image is saved as WEBP with a filename like:

    ```text
    <pdf_stem>_<category>_<sku-tag>_p<page>_img<index>.webp
    ```

- **Filtering / cleaning**
  - Pure grayscale images are skipped (to avoid logos/backgrounds).
  - Filenames are sanitized to be filesystem-safe and trimmed to reasonable lengths.

This helper is useful when you want a pdf24-like dump of all catalog images on disk, but with filenames that already encode the **catalog section and SKUs** they belong to.

## GPT-based image classification enrichment

After generating your main analysis JSON with `Extract.py`, you can run an additional enrichment step that classifies each product image using a vision-capable GPT model.

- **Script**: `classify_images_with_gpt.py`
- **Input**: latest `*_analysis_v*.json` in `output/` (for example `input_pdfs_analysis_v5.json`)
- **Output**: new JSON in `output/` with a name like `input_pdfs_analysis_v5_with_tools_v1.json`

Each image entry under `images[]` can be enriched with fields such as:

- `is_hardware_tool`: boolean flag if the image is a real hardware/tool/pipe/etc. product
- `hardware_tool_labels`: optional list of labels like `"pipe"`, `"valve"`, `"compressor"`
- `hardware_tool_confidence`: optional confidence score in `[0, 1]`

Images that are logos, icons, or decorative graphics are typically marked with `is_hardware_tool = false`.

### Running the GPT enrichment step

1. Ensure you have set `OPENAI_API_KEY` and installed the `openai` Python package.
2. Make sure you have already run `Extract.py` so that at least one `*_analysis_v*.json` exists in `output/`.
3. From the project root, run:

   ```powershell
   py classify_images_with_gpt.py
   ```

4. The script will:
   - Locate the newest `*_analysis_v*.json` file in `output/`.
   - Classify each image referenced by `images[].image_path`.
   - Write a new, enriched JSON file next to the original.

## Webshop feed generation

`input_pdfs_analysis_v*.json` files are the **raw analysis output**: they contain detailed OCR text, per-image metadata, bounding boxes, and many intermediate technical fields.

For use in a webshop, this data is condensed into a cleaner, smaller feed in two steps:

- `output/products_for_shop.json`
  - Built by `build_shop_feed.py` from a chosen analysis file (by default `output/input_pdfs_analysis_v5.json`, but you can point it to `v7`, `v8`, etc.).
  - One entry per SKU, with fields like `id`, `sku`, `name`, `catalog`, `category`, `description`, `attributes`, `specs`, `media`, `price`, `stock`, `seo`, and a simplified `source` block.
  - Designed to be consumed directly by the DemaWebshop project.

- `output/products_for_shop_rewritten.json`
  - Built by `rewrite_media_urls.py` from `products_for_shop.json`.
  - Keeps the same product structure but rewrites `media[].url` to match the public path used by the webshop (for example `/product-images/...`).

Typical workflow:

1. Run the extractor (`Extract.py`) to regenerate the latest `output/input_pdfs_analysis_vX.json`.
2. In `build_shop_feed.py`, set `INPUT_JSON` to the analysis version you want to use (for example `input_pdfs_analysis_v8.json`), then run:

   ```powershell
   py build_shop_feed.py
   ```

3. Optionally, rewrite media URLs for the webshop by running:

   ```powershell
   py rewrite_media_urls.py
   ```

   This produces `output/products_for_shop_rewritten.json`.

4. Copy the resulting feed file into the webshop project (either the original or the rewritten one, depending on your setup):

   ```text
   C:\Users\prova\Documents\Projects\DemaWebshop\dema-webshop\public\data\products_for_shop.json
   ```

5. Restart or redeploy the webshop so it picks up the updated product feed.

The DemaWebshop codebase treats `products_for_shop.json` (or the rewritten variant) as the **live catalog**, while the chosen `input_pdfs_analysis_vX.json` remains the upstream, more detailed source that you can use for future improvements or re-generation of the feed.

### Reducing data loss between analysis and webshop feed

The webshop feed is intentionally smaller than the raw analysis, but you can keep more information if needed:

- **Option A – Use a richer analysis version**
  - In `build_shop_feed.py`, point `INPUT_JSON` to a newer file such as `input_pdfs_analysis_v7.json` or `input_pdfs_analysis_v8.json` if those contain more/better extracted fields.
  - Then rerun `build_shop_feed.py` (and `rewrite_media_urls.py` if you use the rewritten feed).

- **Option B – Preserve more technical fields as attributes**
  - Extend the attribute builders in `build_shop_feed.py` (`build_compressor_attributes`, `build_pump_attributes`, `build_pipe_attributes`, `build_other_attributes`, `build_universal_attributes`) to include additional keys from the analysis JSON.
  - Anything you add to the `attrs` dict in these helpers will appear in both `attributes` and `specs` in the final feed.

- **Option C – Keep a raw debug block**
  - For zero data loss at the cost of a larger feed, you can add the original analysis item under a debug field in `transform_item`:

    ```python
    return {
        ...,
        "source": {...},
        "raw": item,  # or a subset of keys for debugging
    }
    ```

  - This is mainly useful for debugging or internal tools; the webshop frontend may not need or want this extra payload.

## Notes and extensions

- The script uses a set of regex patterns and heuristics; it will not be perfect for all catalogs.
- You can refine SKU patterns or header mappings in `Extract.py` if needed.
- To truly classify images as "airpress", "pump", "pipe", or protective gear, you can:
  - Crop the image regions defined by `images[].bbox` from the original PDF.
  - Feed those crops to a computer-vision or multimodal model.
  - Store the predicted category back into your product JSON.

This README is a high-level overview; see `Extract.py` for all details and advanced logic.
